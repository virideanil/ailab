# Host-managed engine pilot

The current cohort is native-tools-v5: standard assistant tool calls and matching tool observations, with the original request supplied once. The failed host-proposals-v1 tournament remains in docs/validation/004. This is a new execution protocol, not a retrospective repair of earlier scores. All historical reports, smoke prompts and smoke graders remain unchanged.

## Contract
The model proposes reads, literal edits, whole-file writes, optional semantic renames and final answers. The host owns file versions, exact-match validation, atomic multi-file commits, read-before-write requirements, read-only tasks, deadlines and output serialization. An edit proposal cannot invent a version. A finish action does not certify correctness: acceptance belongs to a separate evaluator.

Literal completion formats are enforced from public instructions or public outputContract metadata. Explicit key/value output templates and labeled ISO date requests have a bounded deterministic evidence extractor, shared across all arms. It requires observed source files; missing or conflicting fields yield UNKNOWN. This deliberately moves suitable structured extraction into software. Free-form reasoning still depends on the model; arbitrary hallucinations are not mechanically eliminated. Read-only evidence questions require observed named sources, or the supplied document set when no paths are named, before any answer or abstention can be submitted. This uses only public instructions.

## Frozen diagnostic pilot
48 small JavaScript repairs/renames and 12 grounded evidence questions. Private cases and reference solutions never enter runtime tasks or model messages. The suite identity combines its manifest hash with the exact fixture source SHA-256. This preserves property encounter order, which affects several JavaScript tasks and is not represented by the manifest’s sorted-key canonicalization. Its commit precedes model runs. A correction after observations creates a new cohort; old evidence remains.

The verifier executes candidate code in a resource-limited, unprivileged, read-only Docker container with network disabled. Expected values remain in the host. This is stronger process isolation than a Node vm; it is not a defense against every kernel/container escape. Before model runs, all reference solutions must pass and all broken starters must fail.

## Baseline selection
Compare pinned Qwen2.5-Coder-1.5B, Qwen3-4B and Qwen2.5-Coder-3B GGUF Q4_K_M. Coder-3B is a noncommercial research comparator under the Qwen Research license, not the product default. Qwen3 uses its documented nonthinking sampler and disables thinking in the template. All arms use identical per-model sampling, native function tools through the embedded Jinja template, a 512-token response cap, 12 turns and the same declared cache regime. The unchanged smoke fixtures retain 120 seconds; all frozen pilot tasks retain 30 seconds. Four decode and prefill threads are a declared common configuration, not an experimentally proven optimum. Actual CPU allocation and template metadata are recorded.

All eight original smoke checks must pass before a model enters the pilot. This is an integration gate, not evidence of coding capability. Among eligible models, prefer Qwen3-4B, then Coder-3B research, then the 1.5B reference; publish every outcome. Do not rank latency across different runner machines as a controlled comparison.

## Isolated acceleration
1. Context reuse: current prompt-mentioned files are preloaded with versions, under an 8 KiB content cap. If no path is mentioned and the workspace contains at most three files, preload that bounded workspace. This deterministic policy uses only public task data. Preparation is timed. Baseline reads normally. Pairs are counterbalanced on the same host.
2. Native editing: only the scope-aware TypeScript rename capability is added. Frozen eligibility is p45–p48; this is a four-task diagnostic, not evidence across the full coding population.
3. Prompt-lookup drafting: only llama.cpp ngram-simple is enabled, with n=4 and m=16. It may copy any matching prompt/history tokens, not exclusively source. Target sampling and grammar still verify tokens. Log proposed/target-accepted draft tokens and ordinary fallback. Server metrics snapshots cover the isolated invocation including warmup; response usage covers successfully parsed tool responses only. Missing timing data on an aborted request means unknown, not zero. A zero draft count does not prove no copyable source existed; counters cannot identify whether copied tokens came from source, tool syntax or other history. Draft-token acceptance is distinct from task acceptance.

The initial pilot is exploratory. Preserve assigned tasks, failed runs, invalid runs, grading time and hardware identities. Report accepted tasks and deadline-capped time to acceptance with the declared 80/20 coding/general weights. Never report faster failed completions as improvements. Promote no default based solely on a tiny positive point estimate; any quality regression, missing evidence or unmeasured laptop memory/thermal behavior blocks a broad speed claim. Final laptop admission and sustained performance require the user's actual Mac later.

Warmup is an excluded, one-token native completion without tools or grammar. A warmup failure is recorded and does not erase assigned smoke tasks. Native requests use tool_choice auto with strict one-call validation. The pinned required-tool grammar permits arbitrary prefixes and repeated calls; failed required-tool preflights are retained as separate evidence. Truncated or invalid model responses are retained verbatim in diagnostic events and never executed. No warmup or partial outcome is task acceptance.

For explicitly recognized public Output clauses, the host also validates integers, calendar dates, single identifiers, declared token alternatives and pipe-separated identifier/cents or identifier/status tuples. Invalid presentation returns a format diagnostic within the same task budget; no answer is extracted from explanatory prose. Unsupported natural-language formats remain free-form and are not claimed to be mechanically enforced. Pilot fixtures and private answers remain byte-for-byte unchanged.

The v4 compatibility adapter accepts native function calls or a complete strict JSON {name,arguments} object, optionally inside one whole lowercase json fence. It rejects duplicate members, extra prose/fields, multiple objects, ambiguous fallback envelopes and truncated completions. Every path uses identical tool/argument validation and host authorization. Raw text, finish reason and normalization are recorded. This repairs model serialization without extracting actions from arbitrary prose. Prior v3 framing failures remain preserved as separate results.

A normal completed assistant text response is a final-answer proposal, as in the standard auto-tool API. It is passed to the host completion/evidence/output contract, not interpreted as an edit or scanned for embedded actions. Text beginning with a JSON object or a code fence must pass the strict proposal-envelope parser. Required reads and mutations still apply; a final answer never establishes private acceptance.

## V5 conventional cache baseline

The default CLI cache mode is prefix-warm; --cache task-local reproduces the task-first cache reset as a separate control. Before measured work, one one-token public primer per tool-schema variant warms the model's constant system/tool prefix. Its cost and cache counters are recorded separately as startup. The primer contains no task data and its generated token is discarded, never parsed or executed as an action.

Each measured task then re-primes the same fixed public conversation **inside its deadline and elapsed time**, before any task-specific request. This removes prior task/arm content from the reusable sequence and prevents the second arm inheriting a warmed copy of the paired task. Both baseline and candidate use cache_prompt true. Actual cache_n, prompt_n and prompt_ms remain the evidence of reuse. This is a controlled model/prefix-warm regime, not a cold-start result or a claim that priming is free. Preparation usage is included in task totals; initial startup priming is separate.

Native tool calls remain authoritative when the provider also returns commentary; that commentary is retained, never interpreted as another action. Synthetic IDs avoid earlier transcript IDs. Unsupported raw action frames and array-shaped proposals are rejected. V4 task-cold results remain in validation/008.


## Remaining measurement controls

The native diagnostic alternates different tool schemas in one server slot with no idle-slot cache. Only the last schema remains fully warm; per-task preparation charges schema-switch reprocessing. Label these results single-slot schema switching, not a clean warm comparison of native edit execution. Context arms share their schema, and drafting runs separate server blocks.

After an HTTP timeout, client cancellation does not itself prove that server decoding has stopped. Before interpreting runs after a timeout as controlled steady-state latency, add and validate an observed-idle drain using the pinned server's GET /slots endpoint. Under the exclusive one-slot configuration, require slot 0 with is_processing false (prefer two consecutive observations); unavailable/malformed/busy status must not be treated as idle. Record cleanup separately and retain it in overall throughput wall time. The current CLI does not yet enforce this drain. Existing exploratory reports and deadlines remain evidence, but cannot establish clean post-timeout latency isolation. Failed/cancelled preparation has measured wall time while final token counters may remain unknown.
